## 2. Why — the evidence behind each decision

**Why a monorepo now, and a split only on a trigger.** Ticket #112 measured what the 2026-08-21 brief could only assume. The onboarding cost that motivated v1's three-repository recommendation is a **context-routing** cost, and routing is fixable in place; the thing that actually dominates the repository is **artifact weight, not module coupling** — four dormant dated run-output trees were about **78 % of all tracked bytes**. Splitting repositories would have moved that weight around without removing it, while paying multi-repo overhead on every cross-domain change. The security argument survives, which is why the split is retained as a **conditional** option judged on the security/deployment boundary and on measured cost — and why the trust-zone rule stays binding under **every** topology.

**Why the artifacts leave ordinary Git.** The same measurement: about **1.02 GiB** tracked, one **90 MiB** tree **gitignored yet still tracked**, and dormant run outputs dominating. Indexed, immutable, hash-verified artifact storage addresses the actual cost; Git keeps what Git is good at.

**Why the context architecture takes this exact shape.** The mandated onboarding chain measured about **654 KiB**, of which `GLOBAL_HANDOFF` + `NEXT_STEPS` were about **590 KiB** — and they **structurally regrow through append-only usage after manual rotation**. A cap that a human has to re-apply is not a cap. Hence: history indexed and searched on demand rather than loaded, current handoffs capped and current-only, and one-stage routing so that "read what you need" has a mechanical meaning. `CONTEXT.md` is confined to terminology precisely because every prior general-purpose context file grew into a procedure. Two canonical-home collisions found by #112 (`docs/DEPRECATED_FILES.md` byte-identical to `docs/EXCLUDED_PROJECTS.md`; `docs/ACTIVE_FILES.md` and `docs/DECISIONS.md` colliding by name with different canonical `_AI_MEMORY` files) are why explicit canonical homes are part of the doctrine.

**Why claims and mechanical guards, rather than another review round.** Ticket #113 ranked **fourteen** recorded process-failure patterns. The worst: a **cleanup heuristic nearly queued the checkout backing the live scheduled task for removal**, because **no liveness check existed** — owner review caught it. Second: **two Lead sessions wrote the same shared transport artifacts concurrently**, loss avoided by luck, with `SESSION_LOCK` created **afterwards**. Third: repeated **Windows worktree-removal failures left git state and disk reality divergent**, including multi-gigabyte ACL-locked husks. The cross-cutting conclusion is blunt — **git clean/pushed/mtime cannot establish checkout liveness** — and the corollary is that **the existing audit tiers catch wrong conclusions better than evidence-authoring or process failures**. That is why the answer is a **checked registry and mechanical checks at the delivery boundary**, and explicitly **not** a new audit class.

**Why close-out reconciliation is mandatory.** #113 also recorded that **canonical memory drifts when the real work lives on another branch or ref**. Reconciling current `master`, the work branch and durable tracker state before releasing a claim is the cheapest available fix for the most frequently observed loss.
