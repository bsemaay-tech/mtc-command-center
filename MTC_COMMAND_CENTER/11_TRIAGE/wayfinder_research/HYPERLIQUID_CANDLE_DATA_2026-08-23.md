## Question 1 — What OHLCV/candle history does Hyperliquid expose publicly for perps?

1.1. The public candle endpoint is a POST to `https://api.hyperliquid.xyz/info` with body `{"type": "candleSnapshot", "req": {...}}`. Verbatim from the docs body table: `type* String "candleSnapshot"`, `req* Object {"coin": <coin>, "interval": "15m", "startTime": <epoch millis>, "endTime": <epoch millis>}`.
   Source: https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint (section "Candle snapshot"; also linked with anchor `#candle-snapshot` from ccxt's own docstring, see 2.3). Fetched 2026-08-23.

1.2. For HIP-3 deployer markets, the `coin` field must be prefixed with the dex name, e.g. `"xyz:XYZ100"` — verbatim: *"For HIP-3, you need to prefix with the dex name, e.g. 'xyz:XYZ100'"*.
   Source: same docs page as 1.1.

1.3. The hyperliquid-python-sdk wraps this endpoint as `Info.candles_snapshot(self, name: str, interval: str, startTime: int, endTime: int) -> Any`, which maps `name` through `self.name_to_coin[name]` and posts `{"type": "candleSnapshot", "req": {"coin": ..., "interval": interval, "startTime": startTime, "endTime": endTime}}` to `/info`.
   Source: `hyperliquid/info.py`, method `candles_snapshot` (reported at approximately lines 386–408 of the file fetched from the `master` branch on 2026-08-23) — https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/hyperliquid/info.py. The `interval` parameter is typed as plain `str` with no enum/Literal or module-level interval constant defined nearby — i.e., the SDK does not itself enforce or enumerate the valid interval strings; it passes the caller's string straight through.

1.4. Full documented interval list (14 values): `"1m", "3m", "5m", "15m", "30m", "1h", "2h", "4h", "8h", "12h", "1d", "3d", "1w", "1M"`. This confirms 15m, 1h, 4h, and 1d are all supported.
   Source: same docs page as 1.1, verbatim "Supported intervals" line.

1.5. Response rows contain fields `t` (open time, ms), `T` (close time, ms), `s` (coin symbol), `i` (interval string), `o`, `h`, `l`, `c` (open/high/low/close, as strings), `v` (volume, as string), `n` (number of trades, integer). Docs example row (verbatim): `{"T": 1681924499999, "c": "29258.0", "h": "29309.0", "i": "15m", "l": "29250.0", "n": 189, "o": "29295.0", "s": "BTC", "t": 1681923600000, "v": "0.98639"}`.
   Source: same docs page as 1.1.

1.6. **Verified via live API probe on 2026-08-23**: a single unauthenticated POST to `https://api.hyperliquid.xyz/info` with `{"type":"candleSnapshot","req":{"coin":"BTC","interval":"1h","startTime":<4h ago>,"endTime":<now>}}` returned 5 hourly BTC candles with the identical field set (`t,T,s,i,o,c,h,l,v,n`) as the docs example — e.g. row 1: `{"t":1787450400000,"T":1787453999999,"s":"BTC","i":"1h","o":"77246.0","c":"77128.0","h":"77266.0","l":"77068.0","v":"708.30892","n":8959}`. This confirms the field names/shape and the interval-string format (`"1h"`) match the documentation, and that the endpoint requires no authentication.

1.7. The docs state, verbatim, exactly one sentence about depth: *"Only the most recent 5000 candles are available."* No further clarifying sentence appears before or after it on the page, and the page contains no statement about how to page backward for older data or any total-history/retention-window figure.
   Source: same docs page as 1.1 (confirmed via a second, verbatim-only fetch on 2026-08-23 asking for the exact surrounding paragraph — no additional qualifying text exists around this sentence).

1.8. **Ambiguous / UNKNOWN**: whether the "5000 candles" figure in 1.7 is (a) a per-request response-size cap (caller could in principle move `startTime`/`endTime` and page further back) or (b) an absolute total-history retention limit (data older than 5000 candles at a given interval is not served at all, no matter how you query). The official docs text itself does not disambiguate this. Two AI-assisted readings of accessible sources disagreed: one reading of the Hyperliquid docs page characterized it as a total-history limit; ccxt's own GitHub issue tracker (https://github.com/ccxt/ccxt/issues/23243, "Hyperliquid fetch_ohlcv limit issue") describes it from a user's perspective as "the Hyperliquid API returns up to 5000 recent candles" in the context of a single call, consistent with a per-request reading. No primary source found states this unambiguously either way. What was tried: the Hyperliquid docs info-endpoint page (verbatim re-fetch, no clarifying sentence found), the ccxt `hyperliquid.py` source (see 2.5–2.6, no comment clarifying it), and the ccxt issue tracker (does not settle the question either). Marked **UNKNOWN**.

1.9. Derived arithmetic (a calculation, not a documented fact — contingent on treating the 5000 figure in 1.7 as an absolute per-interval cap): at that reading, maximum lookback would be `5000 × interval duration`: 1m ≈ 3.5 days; 15m ≈ 52 days; 1h ≈ 208 days (~6.8 months); 4h ≈ 833 days (~2.3 years); 1d ≈ 5000 days (~13.7 years). This is arithmetic only, derived from fact 1.7, not an independently confirmed figure.

1.10. **UNKNOWN**: how far back candle data actually goes for BTC specifically (e.g. a listing/launch date for the BTC perpetual on Hyperliquid, or an empirically confirmed earliest-available candle timestamp). What was tried: the Info-endpoint and rate-limits docs pages (no retention-window or listing-date statement found), the Perpetuals info-endpoint sub-page (https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint/perpetuals — no candle-history statement), a web search restricted to hyperliquid.gitbook.io/hyperliquid.xyz for a BTC perp launch/listing date (returned only current trading-UI pages, no dated launch statement), and the hyperliquid-python-sdk source (no constant or comment referencing a start-of-history date). A second live API call that could have empirically tested deep history (e.g. requesting a `startTime` from 2023) was **not made**, because the task authorized exactly one live probe call, which was already spent per 1.6 on a small recent window as instructed.

## Question 2 — Does ccxt support Hyperliquid's `fetchOHLCV`?

2.1. Yes. `describe()['has']['fetchOHLCV'] = True` for the Hyperliquid exchange class.
   Source: `python/ccxt/hyperliquid.py`, `describe()` method, `has` dict — https://github.com/ccxt/ccxt/blob/master/python/ccxt/hyperliquid.py (fetched from `master` branch, 2026-08-23).

2.2. The `timeframes` dict maps all 14 of Hyperliquid's documented interval strings 1:1 (key equals value): `{'1m':'1m','3m':'3m','5m':'5m','15m':'15m','30m':'30m','1h':'1h','2h':'2h','4h':'4h','8h':'8h','12h':'12h','1d':'1d','3d':'3d','1w':'1w','1M':'1M'}`. This is the same 14-entry set documented in fact 1.4 — no timeframe present in the raw API is missing from ccxt's mapping.
   Source: same file as 2.1, `describe()` method, `timeframes` dict.

2.3. Method signature: `def fetch_ohlcv(self, symbol: str, timeframe: str = '1m', since: Int = None, limit: Int = None, params={}) -> list[list]`. Its docstring cites the same docs URL used in fact 1.1, with the anchor made explicit: `https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint#candle-snapshot`. Note: the docstring's inline example of supported timeframes ("support '1m', '15m', '1h', '1d'") is an abbreviated illustrative subset — the actual enforced set is the full 14-entry `timeframes` dict from 2.2, not just those four. This is a minor docstring-vs-implementation wording gap, not a functional restriction.
   Source: same file as 2.1, `fetch_ohlcv` method docstring.

2.4. Request construction: `fetch_ohlcv` builds exactly one `{"type": "candleSnapshot", "req": {"coin": <base/id>, "interval": <mapped timeframe>, "startTime": since, "endTime": until}}` call per invocation — i.e. it is a thin wrapper around the same raw endpoint described in Question 1, not a distinct data source. `since` maps directly to `startTime`; an optional `params.until` maps to `endTime`. If `since` is omitted but `limit` is supplied, ccxt computes a starting timestamp backward from "now" (or from `until`) using `limit × timeframe-in-ms`.
   Source: same file as 2.1, `fetch_ohlcv` method body.

2.5. ccxt declares a default OHLCV fetch limit for Hyperliquid of exactly 5000 in its capability/features block: `'fetchOHLCV': {'limit': 5000}` (found near line ~1445 of the fetched file, inside the exchange's `features` dict). This numerically matches the "5000" figure Hyperliquid's own docs state (fact 1.7).
   Source: same file as 2.1, `features` dict.

2.6. No automatic multi-request pagination loop was found inside `fetch_ohlcv` itself — it issues a single `candleSnapshot` POST per call and returns whatever that call yields (up to the 5000-row cap in 2.5). No comment lines inside or adjacent to `fetch_ohlcv` were found addressing pagination, "since"/"until" chaining, or historical-data availability beyond the docstring's single doc-link.
   Source: same file as 2.1 (absence-of-code-comment observation from a full-text scan of the method and surrounding lines requested from the fetched source, 2026-08-23).

2.7. ccxt's own GitHub issue tracker records a caveat: issue #23243, "Hyperliquid fetch_ohlcv limit issue," reports that ccxt's `fetch_ohlcv` for Hyperliquid did not default to the exchange's true max of 5000, causing friction for callers who wanted only a small recent slice (the reporter's own words: *"it makes it difficult to fetch the last 100 candles for example. First I'd have to know the Hyperliquid API limit of 5000 and pass that to fetch_ohlcv, and then I'd have to grab the last 100 candles"*). A linked pull request, #23244, is referenced as closed. The currently fetched `master` source (fact 2.5) shows `limit: 5000` declared in the features block; this document does not independently confirm whether #23244's diff is what produced that current state.
   Source: https://github.com/ccxt/ccxt/issues/23243 (fetched 2026-08-23).

2.8. ccxt support for Hyperliquid was introduced via pull request #20590, titled "New exchange: hyperliquid," created 2023-12-29 and merged 2024-03-06T11:41:27Z into `master` at merge commit `006c911edd2306294fad839eeba7e7979807645b`. The PR description (per GitHub's PR-search metadata) covers public APIs, private APIs, and EVM signature support — i.e. `fetchOHLCV` support was part of the initial exchange addition, not a later add-on, though this document did not separately diff PR #20590 to confirm `fetch_ohlcv` was present in the very first commit of that PR versus added during its ~2-month review window (created Dec 2023, merged Mar 2024).
   Source: GitHub PR search API, https://api.github.com/search/issues?q=repo:ccxt/ccxt+hyperliquid+in:title+type:pr+sort:created-asc and https://api.github.com/repos/ccxt/ccxt/pulls/20590 (fetched 2026-08-23).

2.9. **UNKNOWN**: the exact ccxt package version/release number (e.g. a PyPI/npm version tag) that first shipped Hyperliquid support. What was tried: fetching `CHANGELOG.md` from the `master` branch (https://raw.githubusercontent.com/ccxt/ccxt/master/CHANGELOG.md) — the file as fetched only surfaced entries from mid-2026 (the top/most-recent portion); the March 2024 section could not be reached within a single fetch due to the file's size, so no version heading could be matched to the March 2024 merge date in fact 2.8. The verified anchors for "when" are the PR creation/merge dates and merge commit SHA in fact 2.8.

## Question 3 — Alternatives for longer crypto perp history (proxy data)

3.1. This repo already contains a working Binance-perpetual-futures downloader built on ccxt: `MTC_COMMAND_CENTER/02_MTC_BACKTEST/src/data/download.py`. Its module docstring states: *"Downloads historical OHLCV data from Binance USDT-M Futures via ccxt."* (line 4). `get_exchange()` (lines 26–50) instantiates `ccxt.binance` with `'options': {'defaultType': 'future', ...}` (line 44), i.e. USDT-margined perpetual futures, not spot. `download_ohlcv(symbol, timeframe, start_date, end_date, exchange_id="binance", max_retries=5, batch_size=1000, ...)` (lines 97–107) is the public entry point; its own docstring states `batch_size: Number of candles per request (max 1000 for Binance)` (line 118) — this "1000" figure is this repo's own code-comment claim about Binance's limit, not independently re-verified against Binance's API docs in this research pass.
   Source: `C:\WFR4\MTC_COMMAND_CENTER\02_MTC_BACKTEST\src\data\download.py`, lines 4, 26–50, 44, 97–118 (as read 2026-08-23; no specific commit SHA captured — read directly from the working tree per task scope limits on git commands).

3.2. `download_ohlcv`'s pagination loop (lines 167–213) calls `exchange.fetch_ohlcv(ccxt_symbol, timeframe, since=current_ms, limit=batch_size)` repeatedly; after each batch it sets `last_ts = candles[-1][0]` (line 193) and advances `current_ms = last_ts + 1` (line 197), continuing until `current_ms >= end_ms`. Results are deduplicated and sorted (`df.drop_duplicates(subset=['timestamp']).sort_values('timestamp')`, line 232) and returned as a `pandas.DataFrame` with columns `timestamp, open, high, low, close, volume` (lines 223–226).
   Source: same file as 3.1, lines 167–213, 223–232.

3.3. A second existing downloader, `MTC_COMMAND_CENTER/03_QUANTLENS/tools/alpaca_download_dataset.py`, covers a separate universe including `CRYPTO_UNIVERSE = ["BTC/USD", "ETH/USD", "SOL/USD", ...]` (lines 61–62) fetched from `CRYPTO_URL = "https://data.alpaca.markets/v1beta3/crypto/us/bars"` (line 29). Its own module docstring is explicit that this is **spot** crypto, not perpetual futures: *"Crypto: Alpaca crypto endpoint, 24/7."* / *"NO spot forex, NO real CME futures here (need other providers)"* (lines 12–13). Its pagination differs from download.py's timestamp-cursor approach: it follows Alpaca's own `next_page_token` field (`token = payload.get("next_page_token")`, line 97; loop breaks when `not token`, line 98) rather than advancing a timestamp cursor.
   Source: `C:\WFR4\MTC_COMMAND_CENTER\03_QUANTLENS\tools\alpaca_download_dataset.py`, lines 12–13, 29, 61–62, 84–99 (as read 2026-08-23).

3.4. Because Alpaca's crypto product here is spot (fact 3.3) while download.py's Binance product is USDT-margined perpetual futures (fact 3.1), download.py is the closer structural analog if the goal is "longer-history perpetual-futures-style candle data" as a stand-in for Hyperliquid perps — Alpaca spot crypto is a different product type on top of being a different venue.

3.5. **Venue-mismatch caveat (stated explicitly, as required by this ticket's scope):** a Binance BTC/USDT perpetual-futures candle is not the same instrument as a Hyperliquid BTC perpetual candle. They are independently operated venues — one a centralized exchange (Binance) with its own matching engine, order book, liquidity, mark-price/funding-rate mechanism, and settlement; the other a separate on-chain perpetual DEX (Hyperliquid) with its own order book, liquidity, and funding mechanism. ccxt itself models them as two entirely distinct, independently maintained `Exchange` subclasses with separate source files (`python/ccxt/binance.py` vs `python/ccxt/hyperliquid.py`) and no shared identity between their symbols, order books, or funding data. Using one venue's candles as a stand-in for the other's is therefore a **proxy**, not a substitute — price/volume/funding figures will differ, sometimes materially, especially around funding events, liquidations, or venue-specific liquidity shocks.
   Source: repo files in 3.1/3.3 (illustrating the two-separate-pipelines-for-two-separate-venues structure already present in this codebase) plus the existence of `python/ccxt/binance.py` and `python/ccxt/hyperliquid.py` as separate files in the ccxt repo (https://github.com/ccxt/ccxt/tree/master/python/ccxt) as structural evidence the two venues are not treated as interchangeable even at the tooling level. No numeric price/funding divergence data was pulled (out of scope for this research pass and would have required the disallowed extra network calls).

## Question 4 — Minimal daily/weekly incremental refresh pipeline requirements

4.1. The relevant endpoint is the same one described in Question 1: POST `https://api.hyperliquid.xyz/info`, `{"type": "candleSnapshot", "req": {"coin", "interval", "startTime", "endTime"}}`. There is no separate "incremental" or "delta" variant documented — every call is a full `startTime`/`endTime` window request.
   Source: same docs page as fact 1.1.

4.2. Incremental fetching would follow a last-close-time-forward pattern: take the previously stored candle's close time (`T`, per fact 1.5/1.6) and use it (or `T + 1`) as the next request's `startTime`, with `endTime` set to "now." This is the same cursor-advance shape already implemented in this repo's Binance downloader — `last_ts = candles[-1][0]; current_ms = last_ts + 1` (`MTC_COMMAND_CENTER/02_MTC_BACKTEST/src/data/download.py`, lines 193 and 197, fact 3.2) — except Hyperliquid's response rows are JSON objects keyed by field name (`row["T"]`) rather than ccxt's positional OHLCV arrays (`candles[-1][0]`).

4.3. Because the endpoint only ever returns up to the "most recent 5000 candles" (fact 1.7, with the per-request-vs-total-history ambiguity noted in fact 1.8), a periodic refresh job that falls behind by more than `5000 × interval` (see the fact-1.9 arithmetic, itself contingent on the 1.8 ambiguity) may not be able to recover the full gap through `candleSnapshot` alone. This is a direct logical consequence of fact 1.7, not an independently documented statement about refresh-pipeline behavior.

4.4. The endpoint requires no authentication — confirmed both by the docs (the "Info endpoint" section documents `candleSnapshot` alongside other unauthenticated info requests, with no signature/wallet fields in the request body per fact 1.1's body table) and empirically by the live probe (fact 1.6), which succeeded with a bare `Content-Type: application/json` header and no wallet address, signature, or API key.

4.5. Rate limits, verbatim from the dedicated rate-limits page:
   - Aggregate REST weight limit: *"REST requests share an aggregated weight limit of 1200 per minute"* — this is **per IP address** (the page's framing distinguishes this "REST request weights & IP limits" section from the separate address-based section below).
   - Per-request base weight: explicitly enumerated endpoints (`l2Book, allMids, clearinghouseState, orderStatus, spotClearinghouseState, exchangeStatus`) carry weight 2, and `userRole` carries weight 60; the page states *"other info requests"* carry weight 20. `candleSnapshot` is not among the named weight-2 (or weight-60) endpoints, so by the documented default it falls under the "other info requests" weight-20 bucket — this is an inference from the enumerated lists, not a line that names `candleSnapshot`'s base weight explicitly.
   - Response-size surcharge specific to candles: *"The candleSnapshot info endpoint has an additional rate limit weight per 60 items returned in the response."* (A separate, differently-worded surcharge — "per 20 items" — applies to a named list of other endpoints: `recentTrades, historicalOrders, userFills, userFillsByTime, fundingHistory, userFunding, nonUserFundingUpdates, twapHistory, userTwapSliceFills, userTwapSliceFillsByTime, delegatorHistory, delegatorRewards, validatorStats`; `candleSnapshot` is called out separately with its own "per 60 items" rate.)
   - Address-based limits: *"1 request per 1 USDC traded cumulatively since address inception"*, with an *"initial buffer of 10000 requests"* and a 10-second cooldown once exhausted (*"an address is allowed one request every 10 seconds"*). Per the fetched page's own wording, *"This mechanism applies to actions only, not info requests"* — meaning `candleSnapshot`, as an info request, is governed by the IP-based 1200/minute limit (plus its per-60-items surcharge), not by the address/USDC-traded mechanism.
   Source: https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/rate-limits-and-user-limits (fetched verbatim 2026-08-23).

4.6. No weight-cost worked example specific to `candleSnapshot` (e.g. "requesting N candles costs exactly W weight") was found on the rate-limits page beyond the "per 60 items" statement in 4.5 — computing an exact weight for a given request would require combining the base weight-20 inference with `ceil(items_returned / 60)`, which this document states as a derived combination of two verbatim facts, not as a directly quoted worked example.

## Relation to existing repo downloaders

This repo already has two independent OHLCV downloader patterns: `02_MTC_BACKTEST/src/data/download.py` pulls Binance USDT-M perpetual-futures candles through ccxt's unified `fetch_ohlcv(symbol, timeframe, since=, limit=)` call, advancing a millisecond timestamp cursor (`last_ts + 1`) across repeated calls and landing the result in a `pandas.DataFrame` (facts 3.1–3.2); `03_QUANTLENS/tools/alpaca_download_dataset.py` pulls Alpaca spot equities/ETFs and **spot** crypto, paginating via Alpaca's own `next_page_token` field and landing the result in per-symbol CSVs plus a JSON manifest (fact 3.3). Because ccxt implements the identical `fetch_ohlcv(symbol, timeframe, since, limit)` method signature for Hyperliquid as it does for Binance (Question 2), the calling shape already proven out in `download.py` is structurally the same shape ccxt exposes for Hyperliquid — the two exchange classes differ in their `timeframes` dict, their `features.fetchOHLCV.limit` (5000 for Hyperliquid vs. this repo's own "max 1000" comment for Binance, fact 3.1), and in the raw endpoint each wraps (`candleSnapshot` vs. Binance's klines endpoint), but not in the top-level call pattern a downloader script would make. For the Question 3 proxy-data alternative specifically, `download.py`'s Binance/ccxt pipeline is the concrete "existing tooling in this repo" capable of producing longer-history perpetual-futures-shaped candle data today; the venue-mismatch caveat in fact 3.5 applies to any use of that data as a Hyperliquid stand-in. `alpaca_download_dataset.py` is included above for completeness (it is the repo's other downloader and demonstrates a second, page-token-based pagination style) but its crypto coverage is spot, not perpetual futures, making it a less direct analog than `download.py` for perp-specific proxy data.
