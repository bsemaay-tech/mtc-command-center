## 0. The identity keys, for reference (§6.7)

| Key | Carries | Stability |
|---|---|---|
| `candidate_id` | `QLC-<yyyymmdd>-<8 hex source-provenance hash>` — family lineage, navigation only | Stable across packages |
| `family_id` | Source/producer/parameter-neighbourhood cluster (§6.6 rule 6) — leakage control, bucket caps | Stable; `UNKNOWN` blocks `LIVE_CANDIDATE` |
| `package_hash` | Deployable strategy semantics only (spec, kernel, params, modules, substitutes, instrument metadata) | Changes on any semantic edit |
| `evaluation_run_hash` | `package_hash` + dataset + cost model + simulator + evaluation config | Changes on dataset/cost/simulator/config edit even if package is unchanged |
| `deployment_identity_hash` | `package_hash` + allocator + allocation policy + Guardian + risk-bucket + economic + runtime + protection + broker adapter + cost lineage | THE key forward/live evidence binds to; any bound-component change mints a new one and resets that environment's clock (brief lines 1387–1457) |

Six evidence classes are declared (brief) to require `deployment_identity_hash` to be usable at all: `TrialRecord` rows, deterministic-replay artifacts, eligibility verdicts, environment-admission decisions, promotion-decision artifacts, rollback records (brief line 1454). The catalog below checks every artifact class against that requirement — planned and current.

### 1.6 Deterministic-replay artifacts (PLANNED — brief §11.3)

- **Where it is planned:** `MASTER_ARCHITECTURE_AND_IMPLEMENTATION_BRIEF_2026-08-21.md:2000-2028`, "11.3 Deterministic replay — resolving the v1 contradiction." Resolves an acknowledged v1 error (C-5): v1 promised any of 100,000 trials chartable in 3 clicks while only storing full artifacts for ~200 — "both are only possible with replay" (line 2002).
- **Mechanism:** non-materialized trials (i.e. not in Tier 2) trigger deterministic replay keyed on **exact kernel code hash + parameters + dataset hash + cost model**, then get cached (line 2026). Cache sits in an **artifact cache that counts against the 20 GB Q9 budget** (mermaid diagram, line 2011). A max replay-time target is proposed at **≤ 60 s** for one strategy×symbol×timeframe, "measured, then fixed" (line 2027). Replay is only possible because the kernel is deterministic (§9.6 test 1) — the property that makes parity testable also makes storage cheap (line 2028).
- **Size/count:** not separately estimated; capacity is bounded by the shared 20 GB budget, not a class-specific number.
- **Growth rate:** on-demand, not batch — one replay artifact is minted only when a user opens a non-materialized trial in the explorer. No background accretion.
- **§6.7 identity keys carried:** **`deployment_identity_hash`, explicitly binding.** "The replay artifact binds to the `deployment_identity_hash` it was produced under (§6.7); a replay whose composite identity differs from the row's is a new artifact, not a reconstruction of the old one" (line 2026). This is one of the six evidence classes the brief requires to carry the composite (line 1454).
- **Status:** not built — same as §1.5, this is the artifact class an explorer must be designed to request/display, not one it can browse today.

## 3. Q9 (20 GB retention budget) — implications for the explorer

Source: brief lines 1994-1999 (§11.2 retention policy), 2011 (mermaid — `CACHE["Artifact cache - counts against the 20GB budget"]`), 2730 (`R-10` risk register), 2824/2875 (`DL-13`/`Q9` decision log).

- **The 20 GB budget covers Tier 2 full artifacts + the deterministic-replay cache — not the Tier 1 catalog.** Tier 1 (~10-25 MB for 100k trials) is comparatively free; the budget pressure is entirely in materialized per-trial artifact bundles and replay output.
- **LRU eviction, with three protected classes that are never evicted: promoted, pinned, and Pareto-front trials** (line 1996). An explorer's "open this trial" action for anything outside those three classes may trigger a replay (§1.6) rather than an instant artifact read — the UI needs to distinguish "materialized, opens instantly" from "will replay, may take up to ~60s" up front, not discover it on click.
- **"The required historical datasets and engine versions to replay any retained trial are themselves retained"** (line 1997) — i.e. the 20 GB budget must also reserve room for dataset/engine snapshots, not just trial artifacts, or eviction of a dataset silently breaks replay for every trial that depended on it. This is a cross-class dependency the explorer's lineage view should surface (a trial's replayability is conditional on a *different* artifact class still being retained).
- **Eviction is logged, nothing disappears silently** (line 1998) — implies a further, uncatalogued artifact class (an eviction log) that the explorer may eventually need to read to explain "why can't I open this trial instantly anymore," though the brief does not yet specify its schema or location.
- **Promotion packets and the future promotion-decision artifact are far smaller and outside the 20 GB pressure entirely** — they are few in number (0 live today) and each is KB-scale, not part of the same capacity conversation as trial artifacts.
- **Net effect on explorer design:** the budget forces the explorer to be replay-aware by construction — it cannot assume every catalogued trial (Tier 1, unbounded count) has a corresponding openable artifact (Tier 2, capacity-bounded). This is the direct architectural reason deterministic replay (§1.6) exists as its own artifact class rather than being folded into Tier 2.

## 4. Cross-cutting finding for the backbone/lineage tickets

Every artifact class that exists **today** (scorecards, backtest reports, research-run outputs, promotion packets, and the registries backing all of them) carries **zero** §6.7 identity keys — not one uses `candidate_id` in the `QLC-<yyyymmdd>-<hex>` form, `package_hash`, `evaluation_run_hash`, or `deployment_identity_hash`. They key on human-composed slugs (`strategy_id`, `research_run_id`, `run_dir` names, ad hoc candidate IDs like `QL_ALPHA_LINK_8EMA_1H` or `QLR_9ZJK8175drM`) and cross-reference each other by **file path string**, not by hash. The lifecycle fold doc's migration rule (§1.7) makes this gap explicit and binding: none of it can be retroactively hash-blessed, so a lineage/backbone explorer navigating pre-migration history must render every one of these classes as identity-incomplete, `CANDIDATE`-capped, `migrated_2026`-tagged evidence — structurally different from anything produced after the Tier-1/Tier-2/replay/ledger design goes live, which is required to carry the full or graduated key set from day one.
