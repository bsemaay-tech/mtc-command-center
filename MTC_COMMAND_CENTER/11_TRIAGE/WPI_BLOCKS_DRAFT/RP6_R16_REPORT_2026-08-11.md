## Why round 16 is a restructure and not another patch

Rounds 10 → 15 each closed one evasion class and each was followed by an audit
that found a subtler one. The round-15 audit named the root cause: the census
works at **physical-line granularity**. It excludes whole wrapper lines
(`grep -v '^[0-9]*:p0_stop() {'`, `WRAPDEF[line]`) and keys definition identity
on `(line, form, name)`. Both discard the COLUMN, and every residual since round
13 has been a way of hiding inside the discarded column:

| round | class | what was thrown away | how it hid |
|---|---|---|---|
| 15 F3 (`wrapline`) | emitter appended AFTER the wrapper's `}` | column | whole-line exclusion |
| 16 F1 (`inbody`) | emitter added INSIDE the wrapper body | column | whole-line exclusion |
| 15 F1 (`defmulti`) | two definitions on one line | column | `(line, form, name)` collapse |
| 16 F2 (`spandecoy`) | decoy + real definition, one line, same key | column | `(line, form, name)` collapse |

Patching each symptom invites the next. Round 16 changes the unit of
disposition instead: **every function definition and every result producer is
dispositioned by its EXACT SOURCE SPAN, and the wrapper exclusion is bound to
DECLARED EXACT BYTES.** Two records at different positions on one physical line
are now arithmetically incapable of comparing equal — not because a special case
was added, but because the identity cannot collide. This is the same
fail-closed-by-construction move that ended the SEC102 command-word regress by
inverting a blacklist into a whitelist.

### F2 (HIGH, Patterns 12/13) — the function identity was a same-line multiset key — UPHELD, CLOSED

**The finding.** `p0_r15_census_funcdefs` is a deliberately over-broad raw
scanner that tracks neither quoting nor inline-comment state and is anchored only
at a line start or after one of `;&|(){}`. `p0_r15_ident` keyed identity on
`(line, form, name)`. Neither side recorded a column, so a false raw candidate in
non-executed text can carry the same key as a real definition at a position the
raw scanner misses: the tokenizer records the real definition, the raw scanner
records the decoy, and the two sorted multisets compare **equal** although the
records refer to different source occurrences.

**Reproduced, executed.** Mutant `spandecoy` inserts ONE physical line:

```text
    [ -z "${P0_R16_SPANDECOY_MUTANT:-}" ] || printf '%s\n' "x; q5_r16() { :; } z"; while q5_r16() { :; }; do break; done
```

- the raw census sees only the **decoy at column 64** (inside the double-quoted
  `printf` argument, after a `;` — an anchor it admits);
- the tokenizer sees only the **real definition at column 90** (after `while `,
  an intra-line position the census is not anchored at);
- bash really defines `q5_r16` from that position.

The round-15 fence returns **rc 0**, `result=PASS`, and prints

```text
ASSERT_MET funcdef_census_reconciled identities=27 raw=27 funcdef=27 paren_form=27 keyword_form=0 unmodeled_names=0
```

over two different source occurrences, with the real definition holding no
disposition at all.

**The repair.** Both mechanisms now emit the COLUMN of the definition-name token
(the tokenizer builds a per-fragment line-start index once and reports
`FUNCDEF line=<n> col=<c> …`; the raw census reports the name token's column for
both the paren and the `function`-keyword shape). `p0_r16_ident` keys identity on
`(line, col, ord, form, name)` and the two sides are compared one for one with
`cmp`, no `uniq` anywhere. The round-16 fence kills the mutant on identical
counts:

```text
ASSERT_MET mutant=spandecoy bash_n=0 killed_by=funcdef_census_reconciled(raw=27,tok=27)
```

`raw=27,tok=27` is the point: the multiset SIZES agree and the fence still fails,
because the spans do not.

### F3 (HIGH, Patterns 12/13) — inventory mutation conserved only for literal names — UPHELD, CLOSED BY REFUSAL

**The finding.** `p0_r15_name_misuse` is a lexical exact-name search. A
variable-mutating builtin whose target is resolved at run time — `printf -v "$n"`,
`read "$n"`, `declare "${n}=v"` — contains no literal inventory name in that
command, so the lexical census could never see it, and the ordered composition
check was multiset-conserving only for the declared literal assignment shape.

**The repair.** The tokenizer now classifies the operands of every admitted
variable-mutating builtin (`declare`, `typeset`, `local`, `readonly`, `export`,
`read`, `mapfile`, `readarray`, `getopts`, `unset`, `let`, and `printf -v`). A
target that is not a **BARE literal identifier** written in the block's own bytes
is `dynamic_variable_target` — UNMODELED, which carried assertion 9 fails on. Any
option the grammar does not model is `variable_builtin_option_unmodeled`; the
admitted option set is a **WHITELIST** (`-a`/`-i`/`-r` on the declaration
builtins, `-t` and `-d <arg>` on `mapfile`), so an unenumerated option cannot
widen what is admitted. New **assertion 21** additionally refuses any literal
target naming one of the three inventory variables. On the real block:
`variable_targets=113 inventory_targets=0 dynamic_targets=0`.

The `invpartial` and `invempty` mutants — which rewrite an inventory half to
`readonly NAME="…"` — now die by the new assertion as well as the carried one:

```text
ASSERT_MET mutant=invpartial bash_n=0 killed_by=tool_inventory_conserved(inventory_half_unextracted(P0_P0_ONLY_TOOLS)),inventory_variable_targets(inventory_variable_target(P0_P0_ONLY_TOOLS@line=356))
```

**Stated plainly: this is a REFUSAL, not a resolution.** The fence does not
compute what variable a dynamic target names; it refuses to certify a block that
contains one. That is the fail-closed direction and it is listed in the residuals
in those words.

  any span the census cannot resolve" had to be EXECUTED rather than asserted;
  `R16_F1_RED` records both fences' dispositions of the same bytes side by side.
- **The span is `(physical line, byte column)`, not a file byte offset.** The two
  are interconvertible given the file's line-start table, and the discriminating
  property the audit required — two records at different positions never compare
  equal — holds identically for either.
- **The exclusion is span-exact in the tokenizer and byte-exact in the three text
  mechanisms.** `p0_r16_drop_wrapper_defs` still drops a whole `grep -n` record,
  but only when that record's line text is byte-identical to a declared wrapper
  definition, and assertion 19 — in the same verdict — proves each declared line
  holds exactly ONE producer. If assertion 19 fails, the verdict is nonzero and
  nothing is certified on an unverified exclusion.
