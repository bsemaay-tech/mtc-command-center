## The unifying principle, and why both findings are one defect

Round 14 made the census's own EXTRACTORS fail-closed. The round-14 audit read
the POLICY and found the same defect one level deeper: the **conservation laws
conserved the wrong quantity**. Assertion 16 conserved LINE NUMBERS where the
property it needs is definition IDENTITY. Assertion 17 conserved a SET where the
property it needs preserves MULTIPLICITY, over an assignment vocabulary narrower
than the one the fence's own tokenizer admits.

The repair is Pattern 12 + Pattern 13 applied to the COMPARISON: **conserve the
quantity the assertion is about — one identity per definition, one disposition
per assignment, multiplicity and order preserved on both sides — and refuse, as
UNMODELED, every token the fence would otherwise have to normalise into something
the shell never bound.**

are certified rc 0 / `result=PASS` by the published round-14 fence:

| Mutant | What round 14 reports | What bash does |

| `q3_r15() { :; }; while q4_r15() { :; }; do break; done` | `ASSERT_MET funcdef_census_reconciled raw_lines=27 funcdef_lines=27 paren_form=28 keyword_form=0`, rc 0, PASS | defines BOTH `q3_r15` and `q4_r15` from ONE physical line — `EXEC_[defmulti]` records `q3_r15 q4_r15`. Round 14 prints 28 dispositions on the same line as the 27 census lines it compares them against |

The second class also falsifies a published round-14 residual, which said a
definition at an intra-line position "would still be recorded by the tokenizer,
and the two sets are compared with `cmp`, so the disagreement fails the
assertion". That is true only while no OTHER definition shares the physical line.

**Repair (Codex's spec, verbatim).** Each raw definition now carries a STABLE
IDENTITY — physical location, ordinal, form, normalised name — and the two
mechanisms are compared ONE FOR ONE, with `cmp`, and **no `uniq` on either
side**:

- `p0_r15_census_funcdefs` — still line-oriented, still tokenizer-independent,
  still deliberately over-broad, still anchored at a line start or after
  `;&|(){}`; it now performs one left-to-right scan per line and emits
  `<line>TAB<form>TAB<name>` for EVERY candidate on that line, including a second
  and third one. The implementation moved from `grep -nE` to a one-pass `awk`
  line scanner because a line-oriented `grep` cannot emit per-occurrence
  identities — it can only report that a line matched. The recognition principle
  is unchanged (the same two regex shapes, the same anchor set) and the
  independence that matters is unchanged: no shared state, no shared code path,
  and no shell model — this mechanism has no quoting rules, no command-position
  state machine and no fragment queue, which is exactly why it can disagree with
  the tokenizer.
- `p0_r15_tok_funcdefs` — the same triple read off the published `FUNCDEF`
  records.
- `p0_r15_ident` — the identity builder used by BOTH sides, so they cannot drift
  in how they are compared. The ordinal is the multiplicity index within
  identical (line, form, name) triples, assigned after a deterministic
  `LC_ALL=C sort`, because the two mechanisms enumerate in different orders (the
  census scans each physical line left to right; the tokenizer scans the main
  fragment and then every command substitution it queued). A permutation is not a
  loss; a multiplicity difference is, and nothing discards it now.
- `funcdef()` in the tokenizer — a definition-name token that is empty, quoted,
  expanded or escaped (`TQ>0 || TE>0 || TX>0 || name !~ ^[A-Za-z_][A-Za-z0-9_]*$`)
  is recorded as `UNMODELED` **and still emitted** as a `FUNCDEF … name=UNMODELED`
  record, so the refusal fails assertion 9 rather than becoming an omission from
  assertion 16. Bash 5.2 refuses every one of those tokens as a definition name
  ("not a valid identifier"), so normalising one would publish a name the shell
  never bound.

On the unchanged block: `funcdef_census_reconciled identities=26 raw=26
funcdef=26 paren_form=26 keyword_form=0 unmodeled_names=0`.

One consequence is worth stating explicitly, because it is the kind of thing an
audit should ask about: a `FUNCDEF … name=UNMODELED` record does reach
`funcs.txt`, which feeds assertion 14's admissible set. It can never do so in a
PASSING verdict — emitting that record also emits an `UNMODELED` record, and
assertion 9 (`tokenizer_no_unmodeled_syntax`) fails the whole fence on it, in the
main body and in `p0_grammar_verdict` alike. The refusal is therefore terminal,
not a name laundered into the admissible set.

**Reproduced.** The tokenizer admits `NAME+=` and `NAME[i]=` as assignments
(`SELF_QA_RP6.md:11549`), while the inventory censuses matched `NAME=` only, and
the composition was reduced with `sort -u` and compared as a set. Both classes

|---|---|---|
| `P0_P0_ONLY_TOOLS+=" awk"` added after the half's declaration, plus `awk() { :; }` | `ASSERT_MET tool_inventory_conserved … names=12`, `ASSERT_MET no_wrapper_shadow … tool_shadow=0`, rc 0, PASS | the block iterates THIRTEEN tools (`x="id getent"; x+=" awk"` → `id getent awk`), and the thirteenth is shadowed by a definition in the same bytes. **Repair (Codex's spec, verbatim).**

- **Every assignment operator, and every mutating builtin.** The assignment
  census matches `NAME(\[…\])?\+?=` at any command position, and
  `p0_r15_name_misuse` then refuses **every mention of an inventory name that is
  neither a `$`-reference nor its one declaration line** — which covers `+=`,
  `[i]=`, `unset`, `read`, `printf -v`, `declare`, `eval`-assembled assignment
  and every form this fence does not model, without enumerating them. That is one
  terminal disposition per assignment: the declaration, or a reason.
- **Ordered multiset for the composition.** The composition references are no
  longer `sort -u`'d. The reference sequence is compared, in source order and
  with multiplicity, against the declared-half sequence, so a repeated half is a
  different composition and fails closed, and every reference has exactly one
  terminal disposition (position *i* is half *i*).

On the unchanged block: `tool_inventory_conserved halves=2 consumed=P0_RO_TOOLS
names=12 handles_bound=6 [P0_STAT=stat P0_READLINK=readlink P0_ID=id
P0_GETENT=getent P0_ENV=env rl=readlink]`.
