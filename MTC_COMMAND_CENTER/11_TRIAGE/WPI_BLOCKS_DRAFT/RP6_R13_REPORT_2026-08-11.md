## Finding 1 (HIGH) — alias/function-indirection. UPHELD, CLOSED.

### The finding, restated

The round-12 tokenizer admitted a BARE command word without binding what that
name resolves to: `cmdword` fell through silently for any bare word that was not
`eval`/`source`/`.`, `p0_stop`/`p0_fail`, `trap`, or `printf`. There was no alias
rule, no function-identity allowlist, and no shadow check, so a name that
resolved through an alias or a shadowing function to an emitter was not caught.

### The repair — three arms

**Alias — closed statically.** The block enables no `shopt -s expand_aliases`
and defines no `alias` (there is no `shopt` in the block at all; the word
`alias` appears only in comments). Non-interactive bash has aliases OFF by
default, so alias indirection is impossible by construction. Assertion 13 checks
both facts and fails closed if either appears.

The D026 arm reflects exactly that scope. A full alias→emit chain cannot be made
RED-clean against round 12, because an alias whose value is an emitter puts the
emitter text into the line census, which round 12 already catches. The only
uncovered concern was the *mechanism's availability*, so the mutant enables the
one thing the assertion forbids.

**Function — closed by binding.** The tokenizer now emits a `CMDBARE` record for
every BARE command word that is none of the special cases. Assertion 14 requires
each to be in the admissible set: the block's own functions, enumerated at run
time from the tokenizer's own `FUNCDEF` records (so the binding is
source-order-independent); a fixed, deliberately over-complete list of bash 5.2
builtins and reserved words; and the one declared sourced-library function the
block calls, `rp0_require_safe_component`. On the current bytes that is **34
distinct bare command words** — 24 block functions, that one library function,
and nine builtins — every one of them bound. A word that binds to a block
function is sound transitively: that function's body is source in the same file,
so its own emitters are already censused.

**Shadow — closed by naming, in three parts.** The kickoff asked that no
function shadow a wrapper/emitter/tool name, and assertion 15 is that check:
`p0_stop` and `p0_fail` each defined **exactly once**, counted from the raw
`FUNCDEF` records; **no** definition carrying a builtin or keyword name; and
**no** definition carrying one of the block's own RO-tool names, read out of the
block's `P0_RP7_RO_TOOLS`/`P0_P0_ONLY_TOOLS` literals so the check cannot drift
from the inventory. The second and third parts are what make assertion 14's
admissible set mean what it says: without them, "it is a builtin" and "it is a
resolved tool handle" would be claims about names the block could have rebound
underneath them. Twelve RO-tool names, zero shadows on the current bytes.

## Finding 2 (HIGH) — command/builtin-prefix. UPHELD, CLOSED.

### The finding, restated

Round 12's `analyze` classified `command`/`builtin`/`exec` as the command word
and then cleared command position, so the EFFECTIVE operand was never passed
through `cmdword`. The indirect-execution rejection for `eval`/`source`/`.`
applied only when that token was literally first; a prefix that changes which
later token bash executes was not modelled.

### The repair — prefix-strip

`cmdword` recognises the three prefixes at command position and calls
`prefix_classify`, which scans past the prefix's own options and redirections and
classifies the first remaining word as the effective command word through the
same policy. The model is explicit and fail-closed:

- `command -v` / `command -V` is a **lookup** that executes nothing — the operand
  is not classified, which is what bash does;
- `command -p` is the prefix's own option; the following word is the effective
  command;
- redirection-only `exec` (`exec 8>&1`) executes nothing — no operand;
- an fd-number prefix of an immediately adjacent redirection is part of the
  redirection, not an operand;
- any other option shape (`exec -a`, `command --`) is **unmodeled** and fails
  closed.

On the real bytes this classifies exactly the prefix sites that exist, and the
tokenizer's own records confirm it: `PREFIX_OPERAND line=398 prefix=builtin
word=type` and `PREFIX_OPERAND line=400 prefix=builtin word=type` — both
operands bound by assertion 14 — plus the `command -v "$t"` lookup at line 789
and the four redirection-only `exec` sites, none of which yields an operand.
None of these is an emitter; the closure is what makes the fence refuse to
certify a future edit that concealed one.

## What the repair does NOT buy — stated, not implied

- **It does not bind the wrapper bodies.** Assertion 15 binds wrapper *names*;
  it does not bind wrapper *bodies* to a frozen hash. A caller could still source
  an unrelated same-name `p0_stop` before this block — the round-7 A4 residual
  this block already discloses. Closing that needs a frozen hash of the wrapper
  bodies and is outside this round.
- **Assertion 14's admissible set is over-complete on builtins by design.** That
  is safe — a builtin is never an emitter, and assertion 15 now forbids a
  definition from rebinding one of those names. The block-specific entries are
  the `FUNCDEF` names plus `rp0_require_safe_component`. A future block edit
  introducing a bare command word that is neither a builtin nor a declared
  function fails assertion 14 closed, which is the intended direction.
- **The tool-name half of assertion 15 is pinned to the current inventory
  shape.** It reads `P0_RP7_RO_TOOLS`/`P0_P0_ONLY_TOOLS` with two `sed` patterns.
  If a future edit moves the inventory to a shape those patterns do not match,
  the list goes empty and that half silently covers nothing.
- **The QUOTED_LITERAL command-word class** is admitted without a binding record:
  its name is contiguous in the source so the line census sees it, and an emitter
  in that class is caught by the existing EMIT path. This block has no such
  command word, so the residual is named, not closed.
- **It is a static source fence.** Its prefix/binding model covers the shell
  dialect this block is written in and fails closed on what it does not model;
  that is a refusal to certify, not a proof of equivalence to bash's own parser.
  `command -v/-V` is treated as a non-executing lookup; other `command`/`exec`
  option shapes fail closed.
- The complete P0 block was still not run end to end. All seventeen frozen
  deploy-channel literals remain `<PIN-AT-FREEZE>`, so no end-to-end `P0 PASS` is
  reachable and nothing here is dispatchable. `shellcheck` is not installed in
  this environment and was not run.
