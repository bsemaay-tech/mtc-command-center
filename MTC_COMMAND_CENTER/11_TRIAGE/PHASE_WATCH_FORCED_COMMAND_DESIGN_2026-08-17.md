# Phase-watch — dedicated read-only forced-command SSH design (T0 finding #3 remainder)

**STATUS: DESIGN + T0 PACKAGE ONLY. NOTHING APPLIED. No KVM2 contact was made to
prepare this. Every server-side change below requires the owner's separate explicit
approval after review.** Prepared 2026-08-17 per owner instruction.

## Problem

The hardened client already pins host/user/known-hosts, disables ssh config
loading, forwarding, and local commands, and uses `IdentitiesOnly`. But
enforcement still lives entirely on the CLIENT: if the Windows side were
compromised, the `baris` key could run arbitrary commands on KVM2. The T0 reviewer
requires server-side enforcement: the key itself must be incapable of anything but
the approved read-only checks. This design also cleanly solves the two activation
blockers (log read permission; backup-dir check) inside the same review.

## Design

### 1. Dedicated keypair (owner-generated; AI never touches key material)

Owner runs locally, himself:

```bash
ssh-keygen -t ed25519 -C mtc-watch-ro -f "%USERPROFILE%\.ssh\mtc_watch_ro"
```

and loads it into ssh-agent. The existing interactive `baris` key stays untouched
for the dashboard launcher; the WATCHER uses only this new restricted key.

### 2. Server-side forced command (the enforcement)

`authorized_keys` entry for the new public key (single line):

```
command="/usr/local/bin/mtc-watch-collect",restrict,from="<owner-IP-or-omit>" ssh-ed25519 <pubkey> mtc-watch-ro
```

`restrict` disables pty, all forwarding, X11, agent, and user-rc. The client's
requested command is IGNORED; the server always runs `mtc-watch-collect`, which
reads `$SSH_ORIGINAL_COMMAND` and accepts ONLY a check ID:

```bash
#!/bin/sh
# /usr/local/bin/mtc-watch-collect  (root:root 0755; reviewed + hash-pinned)
case "$SSH_ORIGINAL_COMMAND" in
  check1) exec systemctl is-active mtc-bridge-first-start ;;   # + status/NRestarts lines
  check2) exec curl -q -sS --max-time 15 http://127.0.0.1:8790/api/status ;;
  check3) exec ls -lh /var/log/mtc-bridge/ ;;
  check4) exec ls -lh /var/backups/mtc-bridge ;;               # only if/when owner defines it
  check5) exec systemctl show mtc-bridge-first-start -p MemoryCurrent ;;
  check6) exec tail -50 /var/log/mtc-bridge/bridge.err.log ;;
  *) echo "refused: unknown check id" >&2; exit 1 ;;
esac
```

(Final script text to be frozen at review; multi-command checks become fixed
compound lines inside the script — never client-supplied.) Check IDs, not command
strings, cross the wire; even a fully compromised client can only pick from the
menu.

### 3. Log-read permission (solves the check3/check6 blocker)

Pick ONE at review:
- **(a) group ACL (recommended):** `setfacl -R -m g:mtc-watch:rX /var/log/mtc-bridge`
  plus a `mtc-watch` system group containing `baris`; journal access via
  `systemd-journal` group membership; or
- **(b) sudoers NOPASSWD** for the exact tail/journalctl command lines, invoked
  inside `mtc-watch-collect`.

### 4. Client change (local, part of the same T0 re-review)

`collect_kvm2_evidence.ps1` sends `checkN` IDs instead of command text and uses
`-i %USERPROFILE%\.ssh\mtc_watch_ro` with `IdentitiesOnly=yes`. The frozen client
table remains as a second, redundant allowlist.

## T0 review package (when owner approves proceeding)

Artifacts: final `mtc-watch-collect` text + SHA-256; the exact `authorized_keys`
line; the group/ACL or sudoers change; the client diff. Application to KVM2 is a
deployment-owner/owner action under its own sentence; then the Aug-19 pair (or a
follow-up round) reviews the applied state.

## Explicitly out of scope

No KVM2 modification now. No key generated by an AI. No ARM/credential/TESTNET
interaction. `WATCH_ACTIVE` stays NO regardless of this design's progress.
