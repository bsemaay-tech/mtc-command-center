## REQ-4 — Parameter provenance is undefined, and V2's F7 repair (one derived commit variable, never `HEAD`) is not carried into a two-object world where the ambiguity is strictly worse

**Subject:** `TC1:107` ("parameterized target producer, parameterized operator recorder"), `:148` (no recorder/producer/launcher byte may change), `:306` ("the recorder's first immutable record line **is specified as** `attestation_prereg_commit=<COMMIT_1B_OID>`"), `:456` (K34's red list includes "HEAD/object/package changed").

**Context:** `MTC_COMMAND_CENTER/11_TRIAGE/WPI_PREREG_DRAFT_ROUND1/WPI_STAGE1_COMMIT1_PREREG_REVIEW_2026-08-15.md:75-79` (F7: the rule "alternates between `HEAD:<path>`/`COMMIT_1:<path>` … it therefore does not yet fix one argv/rc/output contract that gates the socket"); `MTC_COMMAND_CENTER/11_TRIAGE/WPI_PREREG_DRAFT_ROUND1/WPI_STAGE1_COMMIT1_PREREG_DRAFT_V2_2026-08-15.md:19` (V2's accepted closure: "`COMMIT_1` is derived once and every later object lookup uses only `COMMIT_1`; **no later command uses `HEAD`**"); `MTC_COMMAND_CENTER/11_TRIAGE/STAGE1_TO_AUDIT2_EXECUTION_RUNBOOK_V2_2026-08-15.md:301-303` ("clean current object equals Commit 1; recorder verifies procedure/manifest before socket open").

**Analysis.** 1a cannot contain 1b's OID, so a recorder whose bytes are frozen in 1a must obtain it either (a) as a launcher parameter or (b) by resolving a reference at run time. The design chooses neither and says only that the line "is specified as". Route (b) is precisely what F7 banned, and it is now more dangerous because two commits share the ancestry: `HEAD` may legitimately be 1a, 1b, or a later commit at different moments of the same procedure. K34's expectation source is "K33 exact 1b OID" — independent and correct in principle — but its red condition is written against reference *change*, not against the recorder having resolved a *different* object, and no check compares the record's emitted first line to the independently frozen 1b OID after the capture closes (K35 at `TC1:457` covers create-once/close/streams only).

**Failure scenario.** The frozen recorder resolves the commit with `git rev-parse HEAD`. Between Step 10's read-back and Step 12 the operator's HEAD advances by one unrelated documentation commit on the same branch — permitted, since `TC1:139-148` constrains the 1a→1b delta, not later history. K32/K34 compare current state to itself and see no change since their own last observation; the socket opens; the sealed immutable record binds the attestation to the documentation commit, not to 1b. The one-shot grant is spent and the record is, by `TC1:409`, never rewritten. The symmetric failure runs through route (a): a launcher-supplied OID is checked only against what the launcher supplied.

**What settles it.** State the parameter contract: name every parameter of the producer and of the recorder, name the exact committed field each value is read from, forbid run-time reference resolution for object identity, derive one commit variable once from the K33 record, and require the closed record's first line to be compared to that independently frozen OID as a post-close check with its own K-ID.

**Subject:** `TC1:436` (K14 — "**Predeclared** record schema/path plus OS create-once result"), `:141` (`STAGE1_GATEA_FINAL_RECORD.tsv` is only a "sealed copy/provenance"), `:164`, `:168-170`, `:38` (`CANDIDATE_BINDING_SOURCE_POLICY=FRESH_GATEA_FINAL_RECORD_ONLY`), `:385`, `:437` (K15), and §1.2 (`TC1:30-46`), which pins `ALLOCATION_SOURCE_PATH`, `STABLE_EXPECTATIONS_PATH`, `FINAL_CANDIDATE_BINDING_PATH` and `FINAL_ROOT_BINDING_PATH` but has **no** `GATEA_FINAL_RECORD_PATH`.

**Analysis.** "Create-once at a predeclared path" is a real anti-replay control only if the path is fixed in an object that predates the run. Here it is predeclared nowhere: 1a's chain control does not name it, and the allocation row (`TC1:74-86`) mints `BASE`, `P0_RUNID`, `RO_RUNID`, `REMOTE_BASE` and `OPERATOR_RECORD_PATH` but no Gate-A record path. **Failure scenario.** Step 8 runs and seals record R1; A-9's evidence identity is later found ambiguous, so the operator — still inside the authority's time window and still compliant with "only exact A-0..A-9" — re-runs the full sequence and seals R2 at a second operator-chosen path. ## REQ-6 — Operator-tool digests frozen in 1a, plus the no-change rule, make an unrelated OS patch chain-destroying and force a repeat of the mutating staging run

**Subject:** `TC1:90-103` (§1.5 requires concrete `POWERSHELL/PYTHON/GIT/SSH` digests in 1a), `:107` (`COMMIT1A_OPERATOR_TOOLS.tsv` is a 1a procedure member), `:148` ("No … tool-identity … byte may change. A procedure change requires a new 1a, a new separately bound staging authority where applicable, **a new fresh A-0..A-9 run**, and a new 1b"), `:226`, `:242-249` (1b tool fields must byte-equal 1a), `:440` (K18 blocks on any tool blob change), `:450` (K28).

**Context:** `MTC_COMMAND_CENTER/11_TRIAGE/WPI_PREREG_DRAFT_ROUND1/WPI_STAGE1_COMMIT1_PREREG_DRAFT_V2_2026-08-15.md:148-151` — in the contract being replaced, the four tool path/digest pairs live in the root-channel binding consumed by the **final** commit, i.e. they are measured immediately before use, not frozen a staging run in advance.

**Analysis.** The split moves a set of maintenance-volatile local measurements from the last object to the first one and then forbids them to change. Nothing about the safety property requires this: K28 (`TC1:450`) and `TC1:243-249` already rehash the exact absolute paths immediately before Git use and before any socket, which is the check that actually defends the capture. Freezing the digest in 1a adds no independent expectation — the 1a value is itself a local measurement — while converting every future tool update into a chain-reset event.

**Failure scenario.** 1a is created on day 1; the Gate-A run completes on day 2; on day 3 a Windows cumulative update replaces `C:\Windows\System32\OpenSSH\ssh.exe`. At Step 9/10, K18 and K28 go red against the 1a digest. Per `TC1:148` the remedy is a new 1a — and therefore, explicitly, "a new fresh A-0..A-9 run": a mutating install/start/SIGKILL sequence on the staging host must be repeated, and a second `GATE_A_STAGE_AUTHORITY` sentence must be obtained from the owner, because of a security patch on the operator's workstation. The predictable second-order outcome is worse than the first: the operator defers patching the very SSH client that opens the authorized channel, in order to protect the chain.

**What settles it.** Keep the tool **paths** and the "no PATH lookup / rehash immediately before use" rule in 1a, and carry the **digests** as 1b root-channel binding values (where `TC1:242-249` already re-verifies them). Then a tool update changes 1b inputs only, K28 still fails closed on an unexpected binary, and no staging re-run is implied. If the design deliberately wants the digest frozen pre-staging, it must say why and must state this cost in §1.7 — today it states neither.
