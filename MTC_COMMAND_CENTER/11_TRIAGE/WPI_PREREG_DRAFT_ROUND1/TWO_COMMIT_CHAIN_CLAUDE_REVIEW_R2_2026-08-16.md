## R-1 — Step 8B consumes the eight admin facts, but no numbered step produces or verifies them before it runs; K19–K25 sit after it

**Subject:** `TC2:294` ("It may run only after the eight admin/config facts have selected one exact privileged route and authoritative configuration records have bound the intended `ATT01_TARGET_PROCESS_CHAIN`"), against the ordered walk at `TC2:504-533` — steps 1-7 are local document steps, 7A allocation, 7B 1a, 7C Gate-A authority, 8, 8A, **8B**, and only then `9 | Local final-input join including … admin/config` (`TC2:517`). The admin-fact checks K19–K25 (`TC2:616-622`) are unassigned to any step before 8B; §3.1's "all eight admin facts are concrete and independently sourced" is entry-gate item 5 for **1b** (`TC2:323`), i.e. after 8B; §6.1's 8B row (`TC2:553`) lists only authority and safe-close as STOP causes.

**Context:** `MTC_COMMAND_CENTER/11_TRIAGE/WPI_PREREG_DRAFT_ROUND1/ROOT_CHANNEL_RECORD_GAP_2026-08-15.md:178-185` — four of the eight facts are class "(c), then (b)": a decision followed by *independent configuration evidence*, which is what K19–K25 are; `MTC_COMMAND_CENTER/11_TRIAGE/OWNER_DECISIONS_2026-08-16_MORNING.md:14-26` — the admin review is a documentation decision whose output is an input, with no step in this design that receives and freezes it.

**Failure scenario.** The admin review completes and names a wrapper route in prose. The operator obtains the Step-8B sentence with `[EXACT-CHAIN-BYTES]` filled from that prose. 8B runs, produces clean RED/GREEN, safe-closes, and seals its evidence record. At Step 9 the operator finally runs K22 against authoritative server configuration and discovers one extra hop (a PAM-invoked profile, or `sudo` re-exec through a different shell) that the prose omitted. K39 (`TC2:636`) now goes STOP because the evidence chain and the configured chain differ by bytes — correctly, and too late. Per `TC2:88` the retry "needs new owner authority **and a new allocation**"; the allocation is a committed 1a member (`TC2:115-131`), so a new allocation is a new 1a, and per `TC2:191` a new 1a requires "a new staging authority, fresh A-0..A-9 run, Step 8B evidence run, and 1b". A missing ordering constraint therefore costs a second mutating staging run and two fresh owner sentences.

**What settles it.** Add a numbered local node between 7C and 8B (7D) whose product is the eight admin facts frozen in an immutable local record, whose PASS condition is K19–K25 PASS plus K30 over those fields, and make it an explicit precondition in `TC2:294`, `TC2:516`, `TC2:553`, and the §3.1 gate. If the design intends the facts to be verifiable only at Step 9, then say that 8B runs on an unverified chain and state that cost where the owner will read it.

## R-4 — K26's RED arm, K39's exact-chain requirement, and the owner sentence's exclusions are jointly unsatisfiable for a chain-wide enforcement control

**Subject:** `TC2:300` (the authority binds "the exact D026 RED mutation/falsification and GREEN denial arms, including success and failure paths"); `TC2:623` (K26 goes red if "RED does not falsify"); `TC2:309,636` (K39: a different chain is STOP "even if its denial result looks correct"); `TC2:307` (the sentence excludes "configuration" action and any write beyond the one canary); `TC2:219,221` (category 1 is "any effect … that creates, deletes … on `GATEA-STAGING`" and "must be impossible for each command").

**Context:** `MTC_COMMAND_CENTER/11_TRIAGE/WPI_PREREG_DRAFT_ROUND1/ROOT_CHANNEL_RECORD_GAP_2026-08-15.md:185` — the admin review must name "the exact enforcement mechanism", and the natural answers (read-only bind mount, `ProtectSystem=strict`, a mount-namespaced forced command) are chain-wide, not path-scoped.

**Failure scenario.** The admin review names a read-only mount namespace applied to the whole privileged chain as `TARGET_MUTATION_DENIAL_CONTROL`. The owner signs the sentence and the run executes. The GREEN arm attempts the prohibited write and is denied — correct. The RED arm must demonstrate that the same attempt *would* have succeeded absent the control, but on the exact chain nothing can succeed anywhere, including at `[REMOTE_BASE]/d026_mutation_canary`. The two arms produce identical output, so the test does not discriminate and K26 goes red for a control that is in fact perfect. The only ways out are to disable or scope the control (a configuration action the sentence excludes) or to run the arm on a different chain (K39 STOP). The design halts permanently at Step 8B after the owner has signed a one-use sentence and paid for a privileged host run. The mirror-image problem is present for a path-scoped control: there the RED arm *does* create the canary, which is a real category-1 create-and-delete on `GATEA-STAGING`, and `TC2:221`'s absolute "must be impossible for each command" has no exception written for Step 8B's own commands, nor does the no-residue predicate at `TC2:302` address the directory metadata and journal entries a create-then-delete leaves behind.

**What settles it.** State the admissible RED construction explicitly and relative to the control's scope: name where the canary must sit with respect to the control's coverage, what the falsification arm is when the control admits none, and what the design does with a control that cannot be falsified on its own chain (a named STOP is acceptable, but it must be predictable **before** the owner signs, not after). Separately, write Step 8B's authorized canary into §1.9 as a bounded, owner-authorized, disclosed exception to the category-1 rule, in the same voice §1.9 uses for category 2 — otherwise the design demands, in one section, a host mutation that another section calls impossible.

## R-5 — The Step-8B retry rule silently discards the completed staging evidence; the REQ-6 cost analysis was not applied to the new step

**Subject:** `TC2:88` (`PRIVILEGED_EVIDENCE_USE_ORDINAL=1`, "retry needs new owner authority and a new allocation"); `TC2:553` ("No retry, no Step 9, no reuse of Step 8 authority"); `TC2:115-131` (the allocation is a 1a member); `TC2:191` ("A procedure/path change requires a new 1a and, where applicable, a new staging authority, fresh A-0..A-9 run, Step 8B evidence run, and 1b"); `TC2:579-581` (the half-state table offers "safe local evidence state" and "quarantine" but no reconstitution path).

**Context:** my REQ-6, whose whole point was that a chain-reset rule must be stated with its cost, and `TC2:193`, where V2 does exactly that for tools — and then does not do it here.

**Failure scenario.** The 8B run is executed and its close arm cannot prove the no-residue predicate — a foreseeable outcome given that five of the five category-1 surfaces are `UNKNOWN` (`TC2:226-231`). The state is `HOST_STATE_UNKNOWN_QUARANTINE` with no retry. A new attempt needs a new allocation; a new allocation is new 1a bytes; new 1a bytes require a fresh A-0..A-9 run. The mutating staging run and the Gate-A owner sentence are consumed by a failure in a *later*, differently authorized step — and the document nowhere warns the owner that signing the 8B sentence puts the already-completed Gate-A evidence at risk.

**What settles it.** Either state, in §1.7 next to the tool-volatility analysis, that a failed 8B discards the Gate-A run and why that is accepted; or define an allocation-preserving reissue (a second `PRIVILEGED_EVIDENCE_USE_ORDINAL` with its own owner sentence and its own record path, which the R-2 repair makes expressible) so that a safe-closed but failed evidence run does not reset the chain.
