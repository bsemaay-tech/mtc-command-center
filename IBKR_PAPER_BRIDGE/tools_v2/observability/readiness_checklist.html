A · State safety (window honesty & disarm)

A1 · A soak window may show RUNNING only with fresh liveness, ARMED, and no recorded interruption
Plain language

The bridge must never look alive when it is dead. "Running" has to be earned from three pieces of stored proof — a recent health pulse, the armed state, and no interruption on record — never from a claim or a stale value.

Technical

compute_window_state decision order: reset marker → DOWN; no window → DOWN; liveness missing / future-dated / older than stale_after_s (default 300 s) → DOWN; interruption recorded → INTERRUPTED; app_state == ARMED → RUNNING. Unreadable store reports DOWN with error: store_unreadable; unparseable timestamps report DOWN with error: invalid_meta:<key>.

docs/21_WINDOW_STATE_CONTRACT.md:26-42
A2 · Interruptions are sticky — re-arming alone never clears them
Plain language

If the evidence run had a gap, quietly restarting it and calling the whole thing one continuous run would be dishonest. Only an explicit operator-driven reset starts a clean evidence run.

Technical

Only reset_window (no HTTP surface by design — a runbook/Python action) clears window_interrupted_ts. Downtime gaps ≤ stale_after_s (300 s) do not stamp an interruption (brief-maintenance tolerance); while disarmed, the window still shows INTERRUPTED live.

docs/21_WINDOW_STATE_CONTRACT.md:44-53
A3 · Broken window evidence reports DOWN with an error code — never a fabricated active state
Plain language

When the stored proof cannot be read or understood, the honest answer is "down, and here is why" — not a guess that happens to look healthy.

Technical

Unreadable store → DOWN + error: store_unreadable; unparseable non-empty window timestamp → DOWN + error: invalid_meta:<meta-key>; future-dated liveness → DOWN + error: future_liveness; exact-threshold liveness (age == stale_after_s) remains fresh.

docs/21_WINDOW_STATE_CONTRACT.md:37-42
A4 · First detection of an owned partial fill latches DISARMED and opens a recovery row — in one transaction
Plain language

A half-filled position is a situation the engine must stop and hold your hand over, not keep trading through. The moment it is detected, trading is switched off and a recovery case is opened together, atomically.

Technical

First detection writes PARTIALLY_FILLED, opens the partial-recovery row, and latches app_state=DISARMED in one transaction. Reserving CANCEL_ENTRY writes PENDING_CANCEL in the same reserve-before-I/O transaction. Post-SAFE_FLAT recovery generations never downgrade an already-terminal entry order.

docs/22_ORDER_STATE_CONTRACT.md:333-345
A5 · UNKNOWN_SUBMISSION is frozen — no blind retry, ever
Plain language

"I don't know if my order got through" is never resolved by sending it again and hoping. It stays parked until real reconciliation evidence says what happened.

Technical

UNKNOWN_SUBMISSION → {PENDING_NEW, SUBMITTING} is unconditionally illegal. Resolving an ambiguous submission requires reconciliation evidence; a retry after real reconciliation is a new order/decision_uid, never the same order mutating backward.

docs/22_ORDER_STATE_CONTRACT.md:157-164, 174-175

B · Schema (store shape before you trust it)

B1 · Store reports the expected schema_version (v4 baseline = 4)
Plain language

Before reading a store, confirm you are reading the shape you think you are. A missing or odd version number means stop and investigate, not proceed and hope.

Technical

SCHEMA_VERSION_BASELINE = 4; fresh initialization writes meta schema_version = '4'. Versions 5-9 exist but require an explicit initialize(target_schema_version=N) through the proven chain — no silent upgrades.

bridge/store/db.py:268-308, 892-898
B2 · order_identity rows are well-formed (74/75-char ids, legal states, timestamp consistency)
Plain language

The identity ledger has a strict, checkable shape. Rows that do not fit it are evidence of corruption or foreign data and must be treated as a finding.

Technical

intent_id: 74 chars, prefix 'intent-v1:' + 64 lowercase hex; request_id: 75 chars, prefix 'request-v1:' + 64 hex; state ∈ {RESERVED, SUBMITTED, LEGACY_RESERVED, LEGACY_SUBMITTED}; table-level CHECK: RESERVED-class rows have submitted_ts NULL, SUBMITTED-class rows have it NOT NULL.

docs/23_ORDER_IDENTITY_CONTRACT.md:55-75
B3 · Orders are keyed by immutable cloid — re-observation updates mutable fields only
Plain language

Seeing the same order again must update what you know about it, never silently replace what it is. A different order wearing a known ID is an error, not an overwrite.

Technical

No INSERT OR REPLACE on orders. Same cloid + same immutable identity (oid, group_id, order_ref, decision_uid, trade_id, role, qty) → update mutable fields only (status, filled_qty, avg_fill_px, ts_last, order_json). Same cloid + different identity → preserve original row, raise OrderCollisionError.

docs/23_ORDER_IDENTITY_CONTRACT.md:151-160

C · Contracts (order-state & identity rules in force)

C1 · Order state vocabulary is exactly the 11 canonical states; terminal states never leave
Plain language

There is one agreed list of order states and one agreed map of which states can follow which. Filled, canceled, rejected, and expired are dead ends — nothing comes back from them.

Technical

OrderState: PENDING_NEW, SUBMITTING, SUBMITTED, OPEN, PARTIALLY_FILLED, PENDING_CANCEL, FILLED, CANCELED, REJECTED, EXPIRED, UNKNOWN_SUBMISSION. TERMINAL_ORDER_STATES = {FILLED, CANCELED, REJECTED, EXPIRED}: zero outgoing edges except self; same-state replay is always a legal idempotent observation.

docs/22_ORDER_STATE_CONTRACT.md:68-84, 130-142, 165-172
C2 · Unrecognized raw broker statuses fail closed — never default to a live state
Plain language

An unfamiliar word from the broker must never be translated into "probably fine and working". It raises an error instead.

Technical

normalize_raw_order_status maps OPEN/SUBMITTED/PENDING/FILLED/CANCELLED_BY_ENGINE (case/whitespace-tolerant); everything else — non-strings, empty, unrecognized — raises UnknownRawOrderStatusError with reason_code ∈ {NON_STRING_RAW_STATUS, EMPTY_RAW_STATUS, UNRECOGNIZED_RAW_STATUS}. The permissive historical "OPEN" fallback is a known risk this contract removes on its surfaces.

docs/22_ORDER_STATE_CONTRACT.md:88-121
C3 · PARTIALLY_FILLED never regresses to a lower-progress state
Plain language

Fill progress is a ratchet. An order that has been partially filled can finish, cancel, or expire — it cannot quietly become "just submitted" again.

Technical

PARTIALLY_FILLED → {PENDING_NEW, SUBMITTING, SUBMITTED, OPEN} is illegal. PENDING_CANCEL may still receive FILLED / PARTIALLY_FILLED / CANCELED / EXPIRED — authoritative race outcomes always win over a pending cancel request.

docs/22_ORDER_STATE_CONTRACT.md:138-141, 176-184
C4 · Duplicate delivery of the same intent+request is BLOCKED — no broker I/O
Plain language

Sending the same trading idea twice (a replay, a retry, a stuck queue) must not produce two orders at the broker. The second delivery is blocked before anything is sent.

Technical

Reservation protocol: BEGIN IMMEDIATE; no identity → insert RESERVED, commit; exact intent+request exists → BLOCKED (no broker I/O); same intent with different request or a digest collision → IdentityCollisionError + audit event with exc.code. Never submit without a committed reservation.

docs/23_ORDER_IDENTITY_CONTRACT.md:8-10, 127-137
C5 · Persisted events carry structured IDs and codes only — never raw exception text
Plain language

When something fails, the durable log records which thing failed and what kind of failure it was — not free-form error text that could leak anything.

Technical

PLACE_BRACKET_FAILED events persist only structured IDs and exception type name (error_type), never str(exc) or raw messages. Identity finalization failures persist only structured IDs; generic failures persist only the error code.

docs/23_ORDER_IDENTITY_CONTRACT.md:178-186
C6 · Canonical states are derived from durable quantities and validated against the transition table
Plain language

"Partially filled" is not a mood — it is arithmetic on recorded fills, checked against the legal-move map before it is written down.

Technical

canonical_order_state(raw_status, ordered_qty, filled_qty, lot, cancel_reserved): exchange-confirmed terminal raw wins; filled == ordered → FILLED; filled > ordered → quantity-integrity failure; cancel reserved before I/O on a live order → PENDING_CANCEL; 0 < filled < ordered → PARTIALLY_FILLED; else normalized raw. Every derived value is checked against ORDER_STATE_TRANSITIONS via validate_order_transition.
